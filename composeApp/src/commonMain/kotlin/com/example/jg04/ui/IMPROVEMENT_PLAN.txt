Recommendation 1 — Prevent unnecessary allocations & stabilize derived UI lists

Problem: App.kt builds val chatList = chats.values.toList() each recomposition; other places pass whole maps/lists repeatedly.
Change: Memoize derived UI lists and expose stable lists/keys. Example patterns:
Use val chatList by remember(chats) { derivedStateOf { chats.values.toList() } }
Use LazyColumn(items = items, key = { it.topicId }) to give stable keys.
Assessment:
Compactness/Conciseness: + — few lines, small helpers; reduces noisy ephemeral conversions.
Readability/Intuitiveness: + — intent clearer when you explicitly derive and remember UI lists.
Computational Efficiency: ++ — prevents repeated allocations and excessive recompositions, helps diffing.
Flexibility: + — stable keys and derived state ease adding new transforms (sorting, filtering).
Files: App.kt, Conversation.kt, ChatLists.kt

Recommendation 2 — Move navigation state to a stable, saveable holder (ViewModel / Saver)

Problem: NavigationController uses mutableStateListOf local to composition; not saveable across process death and can be recreated unexpectedly.
Change: Provide a Navigator interface implemented by a saveable ViewModel or use rememberSaveable with a Saver for the stack. Keep composables stateless with callbacks.
Assessment:
Compactness/Conciseness: 0 — small additional boilerplate (ViewModel/Saver) but localizes code.
Readability/Intuitiveness: + — single source for navigation state clarifies flow and decouples UI.
Computational Efficiency: + — fewer re-creations; stable state reduces churn.
Flexibility: ++ — easier to add deep links, analytics, undo/redo, and persistence.
Files: Navigation.kt

Recommendation 3 — Extract repeating TopAppBar/Scaffold patterns into small reusable composables

Problem: Several screens duplicate similar TopAppBar/Scaffold setup (ChatTopBar, ChatListTopBar, PlaceholderScreen top bar).
Change: Create a small AppTopBar(title: String, navigation: @Composable (() -> Unit)? = null, actions: @Composable RowScope.() -> Unit = {}) and a wrapper StandardScaffold to pass consistent paddings, insets, and theming.
Assessment:
Compactness/Conciseness: ++ — removes duplicated code across screens.
Readability/Intuitiveness: ++ — naming communicates purpose; reduces noise in screen composables.
Computational Efficiency: + — tiny win (less code executed), mostly neutral.
Flexibility: ++ — centralizes changes (e.g., adding global action button, accessibility tweaks).
Files: ChatLists.kt, Conversation.kt, Navigation.kt

Recommendation 4 — Stabilize model-to-UI mapping and add small typed UI DTOs / adapters

Problem: Code directly uses uniffi.rust_api types inside composables (e.g., UiChat, UiMessage), which may be unstable or have nullable fields and may change with future Rust API updates.
Change: Add a thin mapping layer: data class ChatUiModel(...) and map once in AppModel or a dedicated adapter. Keep composables consuming stable, Kotlin-native, documented fields (and mark immutable).
Assessment:
Compactness/Conciseness: - (adds small adapter code) but reduces logic inside composables.
Readability/Intuitiveness: ++ — composables read as “display model” not raw wire model.
Computational Efficiency: + — do mapping once (in flows) instead of in many composable render passes.
Flexibility: ++ — future Rust changes handled in one place; easier to add computed properties (display initials, formatted dates).
Files: App.kt, Conversation.kt

Recommendation 5 — Make interactive lists more performant and accessible

Problem: Message row selection uses remember { mutableStateOf(false) } inside each MessageCard which is fine for short lists but can become costly for very long lists; animateContentSize() and color animation per message can be expensive when many are visible.
Change:
Prefer a selection model in the parent (map of selected IDs) for multi-selection or persistent selection state.
Limit per-item animations or use low-cost transitions (crossfade, or animate only layout size changes).
Add Modifier.semantics and content descriptions for avatars and buttons for accessibility.
Assessment:
Compactness/Conciseness: 0 — small extra code but keeps per-item composables lightweight.
Readability/Intuitiveness: + — centralized selection logic easier to reason about.
Computational Efficiency: ++ — fewer per-item allocations and fewer simultaneous animations.
Flexibility: ++ — central selection model enables bulk actions, long-press, and syncing with model.
Files: Conversation.kt
